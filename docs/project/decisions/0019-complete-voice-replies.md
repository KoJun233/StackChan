# 0019：设备语音完整合成 LLM 返回内容

- 状态：ACCEPTED
- 日期：2026-07-26
- 工作流：服务端

## 背景

INT-004 使用隐私安全阶段诊断评估语音首播延迟。前三版曾依次尝试句子边界、Unicode 上限和首个文本块后 1500 ms 时间预算。第三版改善了 P95，但实际回复通常在约 20 个汉字附近结束。用户确认该效果来自服务端限制后，明确要求不限制 LLM 回复长度：LLM 返回多少，机器人就完整输出多少。

设备现有 SCV1 协议要求服务端先生成完整 WAV，再由设备校验并播放。本决策不引入流式音频协议，也不改变固件播放和取消语义。

## 决策

- 设备语音回合完整消费 LLM 的所有非空流文本块，等待供应商正常结束后再进入 TTS。
- 不按首个文本块后的等待时间、句子边界、换行或 Unicode code point 数量提前停止 LLM 流。
- 语音附加提示只保留简体中文和不使用 Markdown 的表达要求，不再要求“一句”“简短”或指定字数。
- 正常完成时，完整 LLM 回复同时用于 TTS、SCV1 响应和 assistant 成功历史，保证机器人实际说出的内容与后续上下文一致。
- 既有 30 秒 LLM 超时只作为供应商不可用保护；超时不会把部分文本当作成功回复合成或持久化。
- 既有回合取消信号仍可中断 LLM 或 TTS；取消时沿用 `INTERRUPTED` 历史和 `CANCELLED` 诊断语义。
- 文字聊天、SCV1、ASR/TTS 显式模式、七天隐私安全诊断、数据库结构、固件和生产 HTTPS-only 边界不变。

## 原因

完整性是当前交互优先级。服务端提前停止 LLM 会让答案在语义上被截断，也会使用户误以为模型只能回答约 20 个字。等待完整回复会增加长回答的首播等待和 TTS 时长，但行为更直观，并完全服从用户当前选择。

## 验证

- `VoiceTurnServiceTest` 必须确认多个流数据块和多个句子全部进入 TTS 与成功历史。
- 取消回归必须确认 LLM/TTS 阶段仍可中断，且不会生成成功消息。
- 运行服务端全量测试和 Flyway 空库至 V15，确认没有协议或迁移变化。
- 运行 `git diff --check`、`pnpm docs:check`、文档测试和 LAN Compose 静态验证。
- 部署后由用户使用明显超过 20 个汉字的问题验证回复完整播放；不要求为此刷写固件。
- `219b90b` 已只替换现有 LAN server；健康与网页为 200、Flyway V15、LAN `0.0.0.0:8080`、CoreS3 `717a8b1 / motion_disabled` 心跳正常，近期错误数为 0。用户确认实体长回复完整播放且没有问题，人工验收通过。

## 历史测量

- 原始基线 11 个成功回合：录音结束到播放开始 P50/P95 为 `5788/7210 ms`，服务端 P50/P95 为 `5226/6642 ms`。
- 第三版 10 个成功回合：录音结束到播放开始 P50/P95 为 `6131/6327 ms`，服务端 P50/P95 为 `5535/5809 ms`。P95 改善但 P50 未改善，且回复出现约 20 字的实际截断。
- 上述统计只读取阶段与耗时，不读取音频、转写、回复或认证载荷。

## 后续

若完整回复的等待时间再次成为主要问题，应单独设计可校验、可取消的流式 TTS/音频协议，而不是重新引入隐式文本截断。
