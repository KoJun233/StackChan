# 0037：设备语音采用可协商的有序分段播放协议

- 状态：ACCEPTED
- 日期：2026-08-19
- 工作流：服务端、固件
- 关联：[0007：设备语音与持久提醒](0007-device-voice-and-durable-reminders.md)、[0018：触摸取消](0018-touch-control-and-voice-turn-cancellation.md)、[0019：完整语音回复](0019-complete-voice-replies.md)

## 背景

SCV1 必须等待完整 LLM 回复全部合成为一个 WAV 后才开始播放。较长回复会把整段 TTS 时间叠加到首播等待中；触摸取消虽然能停止完整 WAV，但不能阻止已经取消回合的晚到分片被新状态误用。

## 决策

1. 保留同一设备语音入口和 SCV1。新固件通过 `Accept` 优先协商 `application/vnd.stackchan.voice-turn-stream`，同时声明 SCV1 回退；旧固件和旧服务端继续互通。
2. SCV2 使用严格二进制帧：转写开始帧、从 0 连续递增的 WAV 音频帧，以及唯一的完成或安全错误终止帧。每回合最多八段，未知类型、重复、缺失、乱序、越界和终止后的数据全部拒绝。
3. 服务端等待完整 LLM 回复后按原文和自然标点确定性分段，逐段 TTS、逐段刷新，不截断或改写回复。当前优化去掉“等待全部 TTS”这一段延迟，不宣称 LLM token 与 TTS 并行。
4. 固件只在完整校验当前序号的 WAV 帧后播放，并在完成帧与计数一致时结束回合。SCV2 不把完整回复正文重复发送到设备；服务端仍将完整回复持久化到所属角色会话。
5. 触摸取消同时停止本地播放并取消活动 HTTP 请求。服务端在每次合成和写出前后检查同一回合的取消状态；取消后的晚到 TTS 结果不再写出，固件也不会把旧回合分片带入下一回合。
6. 本阶段不实现播放中插话。只有验证设备回声消除能力后，才单独设计全双工采集与语音打断。

## 影响

- 服务端新增 SCV2 流式响应和确定性分段器；固件新增增量帧解析与逐段播放。
- 异步 HTTP 与设备请求超时统一为 90 秒，覆盖有界连续播放；上传大小、设备 Bearer、回合 ID、诊断隐私和 `motion_disabled` 不变。
- 首播改善必须以实体设备的 `UPLOAD_STARTED -> PLAYBACK_STARTED` 数据确认；在完成实机验收前，任务不能视为已发布。
