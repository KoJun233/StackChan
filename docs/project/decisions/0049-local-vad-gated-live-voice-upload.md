# 0049：本地 VAD 门控的边录边传

- 状态：ACCEPTED
- 日期：2026-09-04

## 背景

CoreS3 在启用 Wi-Fi/LwIP 优先 PSRAM 和 1 KiB HTTP 缓冲后，80,044 字节与 72,044 字节 WAV 已能分别在 286 ms 和 436 ms 内完整上传。继续放大单次写入不能把这段时间稳定压到约 100 ms，反而会重新增加内部 SRAM 连续块压力；此前 4 KiB 路径已在内部 SRAM 历史最低值接近零时出现极慢发送与写超时。

用户确认采用边录边传。需要同时保持本地唤醒与 VAD 隐私边界、八秒录音上限、现有 SCV2 有序回复、触摸取消和旧固件兼容。

## 决策

1. 服务端先增加固定同源端点 `POST /api/v1/device/voice/turn/live`。新固件只在本地 VAD 已命中或用户持续按住说话后打开该请求；命中前不得发送任何麦克风音频。
2. 请求继续使用设备 Bearer、同一回合 UUID 和 `audio/wav`，正文使用 HTTP/1.1 chunked transfer。首块 WAV 头的 RIFF 与 data 长度均为 `0xffffffff`，服务端在完整接收且通过 512 KiB 上限后按实际 PCM 长度重建标准 WAV，再交给既有 ASR。
3. 录音窗口从 250 ms 调整为 100 ms；连续两个窗口越过起始阈值后才确认语音，约 800 ms 静音判定保持不变。连续语音块在捕获期间提交，结束时只保留并补发最后一个 100 ms 静音窗口，使“录音结束到请求体结束”以约 100 ms 为目标，而不是声称整个回合或服务端处理在 100 ms 内完成。
4. 麦克风采集与 HTTP 打开/写入必须运行在不同任务；网络阻塞不得暂停 I2S 采样。HTTP RX/TX 缓冲和每次底层写入继续限制为 1 KiB，上传期间继续暂停 Wi-Fi 省电。音频、流式上下文和 24 KiB 上传任务栈位于 PSRAM，既有 32 KiB 语音控制任务栈保持不变。
5. 固件保留完整的八秒 PSRAM 录音作为有界兼容缓存。只有实时请求在结束前无法打开或写入时，才回退到既有 `/api/v1/device/voice/turn` 完整 WAV 上传；发送终止块后发生的响应错误不得自动重试，以免重复创建对话。
6. 回复继续使用既有 SCV2 帧、取消规则和 SCV1 兼容实现。本次只把设备到服务端的请求体传输与录音重叠，不宣称 ASR 供应商支持流式识别。
7. 发布顺序必须为服务端先、固件后。旧固件继续使用原端点；新固件实机安装仍需单独确认设备、串口、profile、提交和 NVS 策略。

## 结果

- 长语音的绝大部分字节在用户说话时已经到达服务端，停录后只需结束最后一块和 chunked 正文。
- 首个同任务实现虽达到 17–136 ms 的请求体尾部，却在两轮实机录音中被同步网络写入阻塞约 1–1.8 秒，分别只形成 0.3 秒和 1.0 秒的碎片并误识别为“嗯”和“No”；改为独立上传任务是实机证据驱动的必要修正。
- 100 ms 是 LAN 正常条件下的尾部目标，不是网络或供应商延迟 SLA；串口验收记录 `capture_tail_ms`、PCM 字节数和安全堆水位。
- 服务端仍会在完整正文到达后开始 ASR，因此剩余的 ASR、Agent 和 TTS 时间不受本决策直接缩短。
- 若实时端点尚未部署，新固件会在打开/写入阶段安全回退，但正式发布仍必须遵守服务端先行，不能把回退作为长期混合版本方案。
