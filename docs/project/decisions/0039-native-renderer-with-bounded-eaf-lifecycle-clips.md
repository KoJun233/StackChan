# 0039：原生连续渲染与有限 EAF 生命周期片段

- 状态：ACCEPTED
- 日期：2026-08-23
- 工作流：固件
- 相关提交：`71868da`（真机验收候选；最终任务提交由本记录所在提交承载）

## 背景

`MEDIA-002` 已把 CoreS3 显示栈迁移到官方 BSP + LVGL 9.4，并在真机上证明原生
160×160 动态球体可稳定运行约 55 FPS，WakeNet、TTS 和触摸同时正常。下一阶段需要
判断 EAF 或 `esp_emote_gfx` 是否能改善开机、切换和强调动画，同时不能重新引入第二套
长期占用显示总线、破坏语音优先级的渲染路径。

官方 `esp_lv_eaf_player` 0.3.0 支持 LVGL 8/9、RLE/Huffman/JPEG，但要求 ESP-IDF
5.5 及以上。`esp_emote_gfx` 3.0.5 由注册表账号 `espressif2022` 发布，不属于乐鑫
`espressif` GitHub 组织；它拥有自己的任务、解码、缓冲和 flush 回调，需要与现有
LVGL 显示所有权重新协调。

## 决策

- 原生 LVGL 参数渲染继续作为默认、安全回退和所有持续表情的唯一实现。
- 官方 EAF player 只作为可选的有限时长生命周期片段候选，例如开机、角色切换和一次性
  强调；片段结束、失败或取消后必须回到原生渲染器。
- EAF 首次评估只使用项目自有、确定性生成的 160×160 RLE 素材。稳定固件不升级到
  ESP-IDF 5.5，除非候选通过实体设备的显示、WakeNet、TTS、触摸、堆水位和重启测试。
- `esp_emote_gfx` 当前只保留隔离 lifecycle probe，不进入生产显示链。若未来要继续，必须
  以独立任务实现真实动画、唯一显示所有权和可取消 flush，再与 EAF/native 同素材实测。
- 不引入第三方 Emotion Ball 等项目的源码、轮廓点、配色或素材；只保留独立实现的产品语义。

## 原因

同一 ESP-IDF 5.5.5 LAN HTTP Quad 构建中，native 为 1,605,088 字节；RLE-only
EAF 为 1,669,504 字节，增加 64,416 字节，其中自有动画占 53,854 字节。去除未使用
JPEG 解码器后，播放器与接入代码的额外增量约 10,562 字节，适合作为少量片段的容量成本。

Emote lifecycle 构建仅增加 10,688 字节，但它没有链接或运行完整动画和显示刷新，不能据此
宣称更快或更省资源。直接让它接管屏幕会重建一套和 LVGL 竞争的渲染边界，风险高于当前已
验收原生方案所能带来的确定收益。

## 影响

- 默认构建不包含 EAF/Emote 组件，根依赖锁和 ESP-IDF 5.4.4 稳定路径保持不变。
- 实验 profile 使用独立组件目录、依赖锁和 build/sdkconfig，避免候选依赖污染生产制品。
- 若 EAF 真机验收通过，后续资源协议仍需定义严格的帧数、尺寸、时长、解码内存、摘要、A/B
  安装、取消和来源映射上限；不能接受模型下发任意动画数据或 URL。
- EAF 候选 `71868da` 已通过实体成功路径，本文转为 `ACCEPTED`。这只接受“有限片段 +
  native 回退”的架构边界，不代表已经建设多片段资源协议或允许 Emote 接管显示。
