# 0044：个人待办保持本地优先、角色隔离和确认式写入

- 状态：ACCEPTED
- 日期：2026-08-30
- 工作流：服务端、前端、部署
- 相关提交：本地 WORK-003/WORK-004 合并任务提交（见 Git HEAD）

## 背景

只读日历和固定地点天气已经能帮助机器人回答外部事实，但用户自己的临时事项仍只能依赖普通提醒或对话记忆。提醒缺少完成状态和管理视图，记忆又不应承担任务执行语义。直接接入第三方任务服务会扩大凭据、同步冲突和网络依赖，也不能解决模型写操作的确认边界。

## 决策

- 首版待办保存在本地 PostgreSQL，并固定绑定设备与陪伴角色；标题、备注、优先级、状态和可选截止时间是唯一业务事实。
- 页面管理员拥有完整 CRUD；设备 Agent 只得到当前设备和角色最多二十条未完成待办，且永不接收备注。
- 未来截止时间复用现有可靠提醒，不建立第二套调度、TTS 或 ACK 链路；完成、删除或移除截止时间同步取消关联提醒。
- 语音新增和完成必须复用结构化提案、确定性复述、两分钟确认、范围校验和幂等执行；只读查询不进入动作提案链。
- 过期待办不补播提醒，模型不能自动拆解、改绑、删除或批量完成任务。
- 首版不接入第三方任务平台、Apple 提醒事项或日历写入，不修改固件和设备协议。

## 原因

本地模型把个人任务、提醒和角色范围放在同一事务边界内，能在不增加账号凭据和同步冲突的情况下形成可验证闭环。只读 Tool 与确认式写入分离，既让机器人能回答真实待办，又避免普通询问或模型误判产生副作用。复用可靠提醒能继承现有免打扰、离线重试和设备 ACK，而不重复实现高风险投递状态机。

## 影响

- V45 新增 `personal_tasks`，并扩展语音动作约束以接受新增和完成待办。
- 管理端在“提醒管理”下增加标准列表/详情 CRUD；待办与普通提醒仍是两个可区分的业务对象。
- 若未来接入第三方任务服务，必须先定义本地与远端的事实归属、冲突策略、删除语义和凭据边界，不得把本地表静默变成同步缓存。
- 设备固件、现有提醒协议、工作日观察口径和身体安全状态不变。
