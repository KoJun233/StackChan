最新验证：可运行服务端 **536/536**（排除既有八类 Windows loopback 环境受限测试）、隔离 PostgreSQL **V1..V51** 空库迁移及 JAR 打包；控制台 **32 文件 104/104**、类型检查、production build、改动文件 ESLint/Stylelint 和文档检查通过。前端测试采用单进程，构建原生崩溃后限制线程和堆内存复验通过，未修改项目依赖、引擎或构建配置。脚本启动器版本差异见[开发环境](development.md)。

事实校正：旧进展将“结束对话”笼统写为未实现，已标记 STALE 并纠正。固件已有“结束聊天”精确短句识别和退出连续追问路径；本轮复用它补齐服务端确定性回复与会话收尾，未修改固件。已整理[50 项陪伴体验验收场景](companion-experience-acceptance.md)，人工结果全部待执行。正式使用、实体验收和价值观察尚无新证据，不能以测试通过替代陪伴价值验证。

**建议下一阶段把重点从增加功能，转向“多个独立伙伴，记得准确、聊得自然、主动得体”。** 目前工程可靠性、权限隔离和投递治理已有相当深度；最薄弱的是陪伴体验的连续闭环，以及证明它值得日常使用的证据。

不是每个功能都浅，也不是相似功能都应该删。普通提醒、待办、工作简报、外部通知已经共享可靠投递；短期上下文、长期记忆、连续对话各有职责；角色隔离符合你明确选择的“多个独立伙伴”。真正需要收敛的是产品入口、命名、跨功能交互，以及下一阶段投入。

优先处理六项：

1. **自然交流闭环**：明确转题、纠正误解、继续讲、结束对话；验证实际口语，不只验证请求成功。
2. **准确记忆闭环**：同义表达能召回、无关信息不硬套、旧偏好能被纠正、每个角色只使用自己的记忆。
3. **主动陪伴闭环**：短开场 → 用户接受或拒绝 → 自然承接 → 后续尊重偏好，避免只会定时说一句。
4. **收敛入口而保留职责**：主动问候/关心/兴趣资讯归为“主动陪伴”；任务/提醒/通知统一查看，但保留各自业务状态。
5. **修补具体可信度问题**：标题资讯的邀请措辞、待办截断计数、简报长度与时长。
6. **开始真实使用观察**：你还没有正式用过，当前不能认定任何可选功能已被用户抛弃，也不能认定陪伴价值已被验证。

建议冻结扩张：通用插件生态、更多资讯源、复杂任务系统、更多动画格式与编辑器、任意唤醒词训练。备份、隐私删除、认证、诊断和安全更新即使低频也应保留。

## 2. 本次追问确认的评审标准

| 决策 | 用户原意与评审处理 |
| --- | --- |
| 报告用途 | 作为后续项目迭代优化的依据；所有建议给出理由、边界和验收方法 |
| 首要价值 | 有个性、记得我、能自然聊天的陪伴 |
| 角色关系 | 多个独立伙伴，各自有独立记忆；不建议默认共享、混合或迁移记忆 |
| 主动程度 | 轻量主动开场，用户愿意时继续聊；不能以增加播报次数代替陪伴深度 |
| 实际使用 | 尚未正式使用，大多数是开发和测试；需求与留存判断均缺少日常证据 |
| 用户范围 | 本次评价以项目拥有者的桌面使用为准；沿用仓库单管理员、单长期用户边界，不推定商业化需求 |

决策关系为：陪伴优先 → 保留独立角色与记忆 → 深化交流和轻量主动 → 事务能力按是否辅助陪伴决定投入。报告给的是评审建议，不代表已批准所有方案进入开发。

### 证据与成熟度口径

- **代码事实**：存在实现、边界、数据模型或界面入口；不等于运行配置已启用。
- **历史验证**：状态文件记载的自动化、部署或用户实体测试；本轮没有重做这些验收。
- **产品判断**：根据已确认定位做的价值与投入判断；不是用户行为统计。
- **闭环较完整**：入口、执行、结果、取消/失败恢复已有实现，但仍需使用观察。
- **局部闭环**：基础可用，但下一步回应、纠正、维护或使用证据不足。
- **条件能力**：依赖连接、硬件能力或额外实体测验；不能算默认可用。
- **未交付/实验**：不能混入已完成的用户功能。

这里的“生态”同时检查：能否配置使用、是否接入聊天/角色、能否回应和纠错、内容或连接是否可维护、失败和迁移能否恢复。没有插件市场不自动等于生态不完善。

| F24 外部通知互动回执 | 知晓、稍后、完成等调用方声明动作；结果供来源轮询 [E09] | 通知的可选回应机制，不是自动执行外部业务 | **合并进通知功能**。用户说完成仅是声明；不能把播完、知晓、任务完成、外部执行成功当成同一状态 |
| F25 外部通知摘要 | 默认关闭，5–300 秒聚合窗口，同集成/设备/角色最多十条与总长限制；互动项不聚合 [E09] | 减少播报次数，与工作简报内容生成不同 | **保留设置，改称合并播报更准确**。是确定性原文聚合，不是智能内容总结；先等真实通知量再调策略 |
| F26 十四天观察与结束通知 | 固定观察窗口，启动/误播报/来源降级/重启/动作安全聚合，一次性 PASS/FAIL 通知 [E15] | 开发验收工具，不是日常伙伴的一项独立服务 | **下沉诊断，冻结扩张**。日期结束不等于通过，更不等于用户喜爱；单独建立陪伴价值观察，不修改已有冻结门槛 |

| F32 内置 Tool | 当前七个只读 Tool，设备/授权门控、次数与超时约束 [E16] | 能力执行层；不是 Skill/MCP 的替代品 | **核心事实支撑**。显示用途和可用原因；优先时间、天气、日历、待办等真实命中率，避免以工具总数为目标 |

## 4. 相似功能怎么合并，哪些不能合并

**先合用户理解和交互，已有共享机制直接复用；只有确有重复才合并实现。** 当前没有证据支持一次大规模数据库合表或调度器重写。

| 组 | 类似功能与相似点 | 建议合并层次 | 注意事项与验收 |
| --- | --- | --- | --- |
| M01 | 主动问候、个性化关心、兴趣资讯：相同触发/配额/生成/投递链 | 统一“主动陪伴”，内容偏好作为策略；追问承接归入同一闭环 | 保留来源标识与回退类型；无来源内容不冒充新闻；原开关迁移不能自动扩大主动范围 |
| M02 | 主动聊天、无声陪伴、工作返回表情：均产生存在感 | 同一陪伴设置入口，区分有声/无声及工作场景 | 必须独立声音授权；“只无声”绝不启用语音；不混淆工作显式启停与所有陪伴开关 |
| M03 | 角色“主动程度”和设备主动频次：名称均像会主动来聊 | 角色字段建议解释为“对话中的追问风格”，设备设置管理主动开口 | 两者现在分别注入人设与控制调度；不能把选择积极性格自动变成更多播报 |
| M04 | 普通提醒、待办截止、工作简报/休息、外部通知、观察结束：都排队播音 | 统一“将要提醒什么/刚才说了什么”视图和回应入口；复用现有 reminders | 已有统一可靠队列，无需再造一套；保留来源、有效期、离线策略、独立动作与幂等键 |
| M05 | 待办、日历、提醒、今日进度：都回答今天的事务 | 同一今日问答，分任务/事件/提醒；今日进度并入待办 | 不合并真源与状态；待办截止已有提醒，禁止再创建并行普通提醒造成双播；保持角色隔离 |
| M06 | “稍后”“知道了”“完成了”：普通提醒、通知和休息都接受类似回应 | 统一意图入口，依据最近有效播报/待确认对象消歧 | 确认时说出对象；播完≠知晓≠待办完成≠外部完成；歧义时澄清，过期对象不执行 |
| M07 | 工作简报、兴趣资讯、通知摘要：都可能主动占用注意力 | 协调总打扰体验、音频预算、暂停/取消与来源展示 | 内容管线保留：确定性事务事实、受控资讯选题、外部原文聚合不能混成 LLM 自由改写；紧急/明确提醒不能被闲聊额度误抑制 |
| M08 | 短期历史、长期记忆、连续对话：用户都可能称“记得/继续聊” | 统一“对话与记忆”的说明和体验测试 | 保留三个机制：本轮指代、稳定事实、免唤醒续听；不扩大默认采音范围，不跨角色注入历史 |
| M09 | 人设、角色音色、主题、PNG/EAF：共同塑造伙伴 | 一个角色呈现视图关联各资产，原生默认 | 保留多个独立伙伴；V1/V2 互斥槽位明确显示；角色归档的提醒/集成副作用需要预览，不能当普通换装 |
| M10 | Tool、Skill、MCP：都出现在能力设置 | 先展示“能帮我做什么”，类型与认证在高级区 | Tool 执行、Skill 指导、MCP 连接；不能合并授权域，Skill 不因此获得脚本执行或文件权限 |
| M11 | 应用 OTA、唤醒模型、表情包更新；配网与服务地址迁移 | 统一设备维护入口、过程与结果展示 | 安装分区、回退条件和身份保留不同；不能把模型安装当应用升级，也不能把快捷迁移改成清身份 |
| M12 | 观察报告、结束通知、健康诊断 | 观察下沉诊断，结束播报作为观察设置 | 保留原始指标口径；不把工程 PASS 展示成“陪伴体验合格” |

建议后续改造顺序：先改名称/解释 → 增加聚合视图和共享对象解析 → 兼容旧链接/API → 最后凭证据删除冗余入口。每次保留旧配置映射，明确来源、角色和取消行为，避免一次迁移大量用户数据。

## 5. 低价值风险与收缩建议

**目前没有足够证据直接认定某个已实现功能“用户不需要”。** 你明确表示还没正式用过；以下是相对陪伴定位的投入取舍，而非实测淘汰名单。

| 候选 | 为什么可能基本用不到 | 当前建议 | 改进或恢复投入的条件 |
| --- | --- | --- | --- |
| 十四天工作观察的前台常驻与结束播报 | 服务开发验收，难持续贡献聊天或被记住的体验 | 下沉诊断；结束播报可选；不继续扩报表 | 真正需要工作陪伴可靠性回顾时再进入 |
| 通知令牌、回执白名单、聚合窗口等首屏设置 | 只有已有外部消息源的用户才能获益 | 保留高级入口；停止增加无真实来源的适配器 | 连续出现有价值的开发完成/事务消息，再完善对应一个来源 |
| 完整任务管理平台方向 | 容易让陪伴机器人变成额外维护的待办系统 | 保留记事/查询/完成，冻结看板、层级项目、复杂同步 | 实际反复用机器人记录和完成任务，且已出现明确缺口 |
| 复杂专注统计和强制工作配置 | 你首先要伙伴，不一定要监督工作 | 工作模式可选，默认使用不依赖它 | 实际主动选择“陪我工作”，休息反馈持续正面 |
| HN 技术资讯扩源 | 兴趣覆盖窄，标题未必值得聊，容易变播报器 | 保留一个来源试用，先修邀请和承接；不扩源 | 用户主动接受或追问，且该来源真能提供所需内容 |
| PNG 增强、更多动画格式、EAF 编辑器/市场 | 内容制作成本高；一个可用素材的价值尚未证实 | PNG 兼容维护；EAF 先完成一个素材；冻结新格式 | 自定义形象确实提升角色辨识与长期使用意愿 |
| 大量角色预设/资产市场 | 多个独立伙伴有明确需求，但不代表需要大量低质量预设 | **不砍多角色**；先打磨两个明显不同的伙伴 | 两个角色各自有稳定使用场景和记忆，才扩角色库 |
| 任意角色名唤醒训练、过多 FPS 参数 | 提升折腾空间，未必改善自然交流 | 高级参数折叠，先把唤醒可靠性做稳 | 固定词确实构成频繁使用障碍，或存在可测显示问题 |
| 通用 Skill/MCP 平台和市场 | 能连接不等于能直接解决用户问题；安装维护负担高 | 保留安全底座，冻结通用扩张 | 至少一个重复使用、比普通对话明显更好的场景 |
| Emote 第二后端、摄像头/NFC/红外/舞蹈等未交付方向 | 会扩大维护与实体测试面，当前无正式需求证据 | 从近期迭代范围中排除，保持实验/延期标记 | 核心陪伴稳定后，单独证明价值再立项 |

**不建议砍：** 记忆确认与删除、隐私隔离、备份恢复、身份认证、取消/停止、OTA 回退、安全动作门控。它们的价值主要是避免失信与恢复故障，使用频率不是合适的淘汰指标。

真正删除已有功能前应满足：完成合理配置后的真实试用、用户明确不需要、无其他能力依赖、数据导出/归档与回滚路径明确。观察期没用过只支持“继续冻结”，不能单独证明永久无价值。

## 6. 最值得深化的缺口与具体方案

### D01 对话有历史，但缺少明确的转题、纠正与续讲体验

当前已取最近完整轮次，并为天气/日程做有限日期追问路由；这是有效基础。问题是这些技术规则不能覆盖“不是这个意思”“我们换个话题”“刚才没讲完”。状态记录也明确“换个话题”尚未交付。[E01]

建议先实现少量明确对话动作：结束当前话题、恢复最近话题、纠正本轮对象、继续上次回答。短期话题状态与长期记忆保持分离；“我不是问游戏，是问工作”只改本轮意图，不自动改用户兴趣。短回答之后“详细说说”应按请求续讲，不优先恢复历史多段 TTS 方案。

验收：包含明确转题、代词、省略、纠正、超过 30 分钟、失败轮次、多角色切换的场景；既不强行续旧题，也不每次要求用户重说全部背景。实际设备延迟和措辞另测。

### D02 记忆治理已有深度，准确使用仍需证明

当前有确认、替换、停用和角色隔离，检索使用文本相似度排序并最多取八条，查询没有看到最低相关性过滤。由此可确认的是“可能把低相关候选提供给模型”，不是“已经发生了错误回忆”；同义表达召回质量也不能仅凭 SQL 推断。[E04]

建议以两个独立角色各自的兴趣、称呼、习惯、近期变化构建小样例集，区分漏召回、错召回、错引用、过时记忆和错误归属。先规范主题与别名、让无关查询不强行引用、完善确认替换；再依据失败类型决定检索升级。

用户说“我现在不喜欢这个了”时，应能明确指出要更新哪条记忆，并按现有确认边界生效；旧值不再参与主动关心。提供简明的“这个角色记得你什么/为什么提这个”与遗忘范围。不能自动把角色 A 的了解分享给 B。

### D03 主动陪伴目前更像开场生成器，缺少反馈后的长期变化

现有调度、额度、免打扰和失败回退较完整；已播放消息也能进入后续语音上下文。下一步应围绕“要不要聊、聊什么、什么时候别聊”而不是增加随机规则。[E05、E06]

建议支持轻量回应：“聊聊”“换个话题”“这个别再主动提”“今天安静点”。区分单次拒绝、当天暂停、长期话题偏好，不把一次“现在忙”永久判为不感兴趣；当日暂停不能未经说明取消用户自己创建的到期提醒。无需用情绪监控替代明确选择。

验收：接受后能接两轮，拒绝后不追问、不立即换话题继续打扰；次日恢复语义清晰；切换角色后遵守角色归属和设备级静音规则。

### D04 资讯邀请与后续资料能力不匹配

代码拼接“标题是……想听听吗？”，但追问上下文明确仅有标题和链接，没有全文。用户回答“好，展开说说”时，目前只能可靠说明标题和一般概念，不能保证介绍原文细节。这是**能力承诺缺口**，并非已证实模型发生幻觉。[E06]

低成本修正：改成“要聊聊这个话题吗”，在展开时说明是一般讨论；需要“介绍这篇文章”的内容，必须先有可核验摘要或正文及来源。先验证需求再接正文抓取，后者还需失败处理、长度预算、来源质量与不可信内容隔离。

HN 官方 API 将 `time` 定义为条目创建时间；不是所链接原文的首发时间。报告及后续界面应继续称“收录/条目时间”，不能据此宣称某项技术刚发布。[Hacker News 官方 API](https://github.com/HackerNews/API#items)

### D05 待办截断计数存在误导风险

未完成查询 `findTop20...`，今日完成最多十项；Tool 返回 `tasks.size()` 和 `completedToday.size()`，没有总数/是否截断字段。超过上限时，返回的是本次展示条目数；若模型把它回答成总量，会低估真实任务数。[E07]

建议保留详情上限，单独返回真实聚合总数与 `hasMore`，或明确命名 `returnedCount` 并禁止当总量。验收用 21 个未完成、11 个今日完成以及跨设备时区边界；页面/Tool 的总数一致，语音可先列少量标题。无需扩建统计系统。

### D06 简报有条目上限，仍可能太长

工作简报可直接拼接两项日历标题，解析后的单标题允许较长文本；最后没有统一的语音时长预算。设计的“约二十秒”不是代码保证，实际时长仍取决于音色和语速。[E10、E11]

建议给所有自动简报设置总字数与估计时长预算，各来源分配限额；只播关键信息，其余可问。截断不得制造日期/事项歧义，也不能让截断标题影响用户确认操作对象。用长中文、英文混排、私密日历、两项待办和单来源失败组合，在实际音色下验收。

### D07 缺少跨来源统一的打扰体验

可靠提醒已保证单设备投递互斥，主动聊天也有额度，但工作简报、普通提醒、外部通知和随机开场的总和，仍可能让用户觉得频繁被打断。“同一时刻只播一条”不等于“这个小时不会连续播很多条”。[E05、E09、E10]

建议先统一暂停和取消含义、显示未来待播来源，再基于真实使用考虑分级预算：用户明确要求的提醒、工作场景提示、可推迟的闲聊和资讯分别处理。不要简单设一个硬上限吞掉提醒；新策略需要有延后/过期原因、来源可见性和回归样例。

### D08 工程 PASS 与陪伴价值之间缺一层观察

工作观察的活跃日只要求当天有显式启动；来源降级检查有无归因，动作失败为零也不证明曾实际执行动作。它没有衡量自然聊天、记忆准确、主动被接受或用户愿意再用。[E15]

用户本次确认还没正式用过，因此历史观察窗口即使到期或后来得到 PASS，也不能据此写成十四天陪伴留存成功。本轮未读取最终结果。保留现有冻结口径，另做第 8 节的小规模价值观察。

### D09 数据库可恢复，整机迁移还需补齐证据

现有 PG 备份和隔离恢复是真实能力；Skill 正文位于独立卷，加密配置迁移依赖原主密钥，不能仅恢复数据库就推定新机器完全可用。[E17]

建议准备分离保管的恢复清单：数据库、Skill 包文件、加密主密钥保管方式、部署版本与必要配置、设备重新连接步骤。密钥不写入报告或仓库。先在隔离环境验证读取角色/记忆、解密配置、读取 Skill 和登录；覆盖生产库或迁移设备是另行授权的任务。

## 7. 建议迭代顺序与交付边界

以下是排序建议，不是已授权的实施清单；规模是相对复杂度，不是工期承诺。

| 顺序 | 任务 | 交付结果与价值 | 规模 / 前置 |
| --- | --- | --- | --- |
| P0-1 | 配置两个独立伙伴，开始真实使用基线 | 确认音色/性格/记忆区别；获得十余段自然交流和主动反馈样例 | 小；保持已验证安全配置 |
| P0-2 | 修 D04/D05/D06 的可信度缺口 | 邀请不超能力，任务总数不误导，简报不因长标题超出预算 | 小至中；局部回归和实际音色测量 |
| P1-1 | 自然对话转题、纠正和续讲 | “理解错了—纠正—继续”成为可验收闭环 | 中；先固定场景集，保留取消/单 WAV |
| P1-2 | 长期记忆准确性与维护 | 同义召回、旧偏好替换、无关不引用、角色不串记忆 | 中；依失败样例选最小改造，不先选向量数据库 |
| P1-3 | 主动接受/拒绝/暂停闭环 | 轻开场后能聊、能拒绝、以后尊重反馈 | 中；先定义临时/长期作用范围和确认边界 |

| P2-2 | 两个角色的表达一致性 | 性格、措辞、音色、表情辨识度稳定；可选一个 EAF 素材 | 中；核心对话先达到可用水平 |

建议每轮只改一个主要体验问题，同时处理少量局部可信度修正；不要一边更换模型、扩大历史、改 TTS、改主动频率，一边试图判断哪项让体验变好。

## 8. 一次可执行的真实使用观察

建议先进行十四个自然日的私用观察。该长度便于跨工作日/周末取样，**不是统计学结论，也不替代既有 WORK-002 窗口**。本轮不自动启用或开始新观察。

选择两个你真的想交往的独立角色，各准备少量不敏感事实；允许其中一个是主用角色，不强迫均等使用。工作陪伴、日历、资讯和通知按实际需要配置，未配置项目记为“未评估”，不是“不需要”。每天只做一分钟本地勾选，不保存新的正文遥测。

| 观察项 | 记录方式 | 建议进入下一轮的判断 |
| --- | --- | --- |
| 自发交流意愿 | 今天是否因想聊天而唤醒，排除测试操作；明天是否愿意继续 | 连续两周仍愿意主动用，比启动次数或在线时长更有意义 |
| 对话承接 | 对实际发生的转题/纠正/省略标对或错，并记错误类型 | 建议固定至少 20 个场景样例，目标 ≥18 个接得住；是拟定验收线，不是现有成绩 |
| 记忆准确性 | 应记住时是否记得；是否引用无关/过时记忆；角色是否串用 | 建议 20 个正/负样例，召回与引用分别评估；跨角色泄漏、未确认记忆生效均应为零 |
| 主动是否值得回应 | 实际听到后：愿聊/现在忙/不感兴趣；是否感觉打扰 | 分开“当前不方便”和“话题不喜欢”；样本少时只看案例，不算漂亮接受率 |
| 控制是否可靠 | 停止、今天安静、稍后、换角色后是否符合预期 | 测试场景全部符合已定义语义；拒绝后不能立即再打扰 |
| 语音体验 | 停止说话到首个可听回应、听错需要重说次数 | 先记录当前中位/P95和噪声条件，再比较同口径迭代；不把服务器耗时当端到端体感 |
| 辅助功能净价值 | 用到时是否减少操作；是否变成又要维护一套系统 | 两周后按具体体验保留/折叠/冻结，不靠菜单点击次数裁撤保障功能 |
| 两个角色辨识度 | 同一主题下能否感到不同性格且记忆归属正确 | 不仅颜色音色不同；各自的边界、称呼、兴趣承接一致 |

新增体验的最低场景应覆盖：

1. A 角色知道一个偏好，B 不应知道；切回 A 仍可召回。
2. 告诉 A 偏好变化，确认后旧值不再被主动提起；B 不受影响。
3. 聊天气后问“那明天呢”，再明确转到游戏，随后“明天呢”不能误继承天气。
4. 主动消息后说“说说看”，能区分标题事实与一般解释；说“不聊这个”后不强追问。
5. 长回答后要求“继续”，有承接；触摸停止后晚到音频不播放，下一轮正常。
6. 待办达到 21/11 条、长日历标题、断网/过期缓存，回答和降级不误导。
7. 工作休息与外部消息相邻播报，“稍后”确认正确对象；播放 ACK 不完成任务。

这些是后续验收样例，不是本次新增或已执行的测试。
